# 连续纵向滑动与仿真翻页延迟优化

日期：2026-10-28（Asia/Hong_Kong）。候选版本：0.9.11 / code 29。

## 已实现的连续滑动行为

阅读菜单的“阅读设置”和全局“默认阅读方式”均新增 **连续滑动（无缝）**。

- 漫画图片按原比例适合宽度，纵向首尾拼接，图片之间不加间隔。原图自身的白边保留。
- 手指上下拖动，列表连续跟随；松手后阻止惯性位移，保留当前位置，不吸附到页首或页尾。
- 支持停在一幅图片中间，并沿用逐页位置和图片内比例保存、恢复。
- 到本章末尾保留当前位置；通过“进入下一章”按钮换章，避免拖动或松手时被自动换章打断。
- 保留左右点击区按屏高滚动、中间菜单、双击和双指缩放。未放大时外层横向滚动关闭；放大后可横向平移，同样限制松手后的惯性。

新增持久化值为 `scroll`，追加到原模式列表末尾。旧 `webtoon`（无缝条漫）和 `continuous`（间隔连续）保持原设置值。新模式复用 `WebtoonViewer`、`StripModel` 和原图片分块链路；不增加另一套图片缓存、数据库表或迁移。

实现通过 `onScrollFrameBegin` 保留拖动位移，并将 `ScrollState.Fling` 阶段的实际位移置零；滚动停止时再保存位置。[OpenHarmony 官方滚动接口说明](https://github.com/openharmony/docs/blob/master/zh-cn/application-dev/reference/apis-arkui/arkui-ts/ts-container-scroll.md)定义了回调返回实际滚动量的契约。本机 API26 SDK 的 `list.d.ts`、`scroll.d.ts` 同时核对；不是将 `flingSpeedLimit(0)` 当作关闭惯性——本机 SDK 明确规定该值会恢复默认速度。

## “正在准备…”对应的实际等待

当前生产路径是：

```text
图片文件可用
  → 可见分块解码和绘制完成
  → PagerSlot.complete()
  → 组件视口截图（等待渲染完成）
  → 后台读取 PixelMap、复制及转换像素
  → EGL 线程上传纹理
  → GPU 纹理就绪
  → 手势曲面绘制
  → 末帧呈现确认
  → 提交页码，交接静态页面
```

`HorizontalPager.dragTo()` 在目标页已显示就绪但纹理尚未就绪时，会将拖动位移归零并显示“正在准备翻页纹理…”。`settle()` 对点击或松手完成动作也会等待同一准备过程，提示“正在准备翻页画面…”。因此，“文件已缓存”不等于“仿真翻页纹理已就绪”。

这里是已从代码确认的等待机制；截图、解码、像素复制、上传各自占了多少毫秒，以及哪一步在目标平板上占主导，本轮没有真机分段计时，不能据此下定论。

截图继续使用 `waitUntilRenderFinished: true`，避免引入之前的局部空白问题。华为官方示例同时说明了截图参数和渲染完成等待的使用方式，见[组件截图说明](https://developer.huawei.com/consumer/cn/doc/doccenter-dev-faq/faqs-arkui-1410)。

## 本轮已落地的第一步优化

原来 `CurlFrameStore` 和 `CurlGpuBridge` 分别对截图、上传去重，但整个 `capture()` 流程没有去重。目标纹理还未就绪时，每次拖动更新仍会：同步缓存保留列表、进入异步等待、追加完成回调，并在完成后再次调用 `dragTo()`。

现在 `HorizontalPager` 以完整纹理键共享同一个 Promise，覆盖 **截图 → 上传 → 完成通知** 全流程。等同一帧的所有手势更新复用这个工作；失败或完成后删除任务，允许重试。原有纹理版本、视口/绘制修订隔离、文件引用和 GPU 末帧确认继续生效。

在生产手势方法的宿主检查中，模拟一次纹理上传尚未完成、连续 41 次拖动更新：

| 指标 | 修改前 | 修改后 |
|---|---:|---:|
| 上层缓存同步次数 | 41 | 1 |
| 修改后的上传桥调用次数 | 未作为基线报告指标 | 1 |

**这不是 41 倍帧率提升，也不是 41 倍等待时间缩短。** 底层实际上传在修改前已去重；本次消除了上层重复工作及回调堆积。第一次冷截图和首次上传仍然需要时间，两条“正在准备…”提示仍可能出现。

## 后续推荐方案

建议按下列顺序推进。以下均为方案，未混入本轮已实现内容。

### 1. 先测各阶段，再优化预热调度

现有代码已经预载当前、前后相邻三个单页/双页组，并在图片就绪时准备纹理。继续增加“普通图片预加载数量”无法直接解决 GPU 纹理冷启动。

下一步应为帧键记录：图片就绪时间、截图开始/结束、后台像素读取/转换、GPU 上传结束、首个有效呈现，以及纹理命中/失效原因。用合成图统计冷进入、连续正向、立即反向、缩放后恢复及旋转后的等待分布。

在现有三组窗口内，把准备工作按“当前页 → 用户正在请求的目标 → 阅读方向下一组 → 另一侧”调度，限制同一时刻的大截图/上传数量。方向变化只提升所需目标；退出、换章、视口变化及时淘汰旧代任务，不取消用户当前可见的页。是否串行截图、是否并行一次截图与一次上传，由分段计时决定。

验收重点是纹理命中率、首次有效曲面时间、输入响应和内存峰值；不能只看网络缓存命中率。

### 2. 用分块图像直接合成卷页纹理，逐步绕开组件截图

这是更有潜力缩短等待链路的方案：复用已解码分块，通过原生合成或离屏绘制生成当前视口纹理，使卷页资源准备不依赖整个 ArkUI 组件树的截图栅栏。预期收益是减少组件截图等待；实际收益需原型计时。

模块边界建议：

- `ReadingCanvas`/双页布局提供不可变视口描述：页身份、缩放、裁剪、背景、上下空白、书脊边距和窄中缝。
- 图像层借出受引用保护的分块资源，不把组件实例或数据库对象交给原生层。
- 独立纹理合成层完成分块到视口的映射和合成；`CurlGpuBridge` 继续只负责纹理提交和呈现。
- `HorizontalPager` 保持手势与页码交接职责；不在手势更新中解码、截图或等待上传。

难点是长图局部位置、双页最后单叶、LTR/RTL、缩放/适配模式，以及静态图和合成图像素位置完全一致。必须保持纹理固定到本次手势结束，再交接静态页面，避免半途替换产生抖动或白块。

### 3. 冷启动仍慢时，再评估两级纹理

可以先为三组窗口准备受预算限制的交互纹理，空闲时升级清晰纹理；一次翻页内固定同一版本，不在拖动中换分辨率。它能减少初次纹理搬运量，但会有翻动时清晰度取舍，需要单独确认可接受程度。

不建议直接关闭渲染完成等待、把目标页标为假就绪、无上限增加纹理缓存，或仅删除等待文字。这些做法无法消除实际阻塞，并可能带来白块、错页和内存问题。若考虑“纹理未就绪先平移页面”的降级效果，应单独确认交互；本轮没有替换仿真曲面。
